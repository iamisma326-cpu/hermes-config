# gestionest1-dev — desarrollo del sistema gestionest1

Patrones, convenciones y pitfalls verificados del sistema "Instituto Argentina" (~/projects/gestionest1). La BD se diseña SIEMPRE con la skill `mysql-architect`; esta skill cubre el resto del sistema y la integración completa.

## Mapa del sistema
- **BD**: MariaDB local `gestion_estudiantes` (60 tablas, 3NF con `personas` raíz; las 4 whatsapp_* desde v2.2.0). Visible en phpMyAdmin (http://localhost/phpmyadmin). Schema vivo: `api/sql/01_schema.sql` (estado final instalable desde cero), migraciones versionadas en `api/sql/migraciones/`, seeds re-ejecutables `03_seed.sql` + `05_seed_soporte.sql` + `06_seed_egresados.sql` + `api/sql/mariadb/11_whatsapp.sql`. Demo limpio: `mariadb -u root < api/sql/03_seed.sql && mariadb -u root < api/sql/05_seed_soporte.sql && mariadb -u root < api/sql/06_seed_egresados.sql && mariadb -u root < api/sql/mariadb/11_whatsapp.sql`.
- **BD PostgreSQL (2026-09-12)**: migrada a PostgreSQL 18.6 como BD `IstArgentina` (nombre case-sensitive: SIEMPRE citar con comillas dobles o conectar con `-d "IstArgentina"`), corriendo EN PARALELO (MariaDB intacta como fuente de verdad). Artefactos: `api/sql/01_schema_pg.sql` + `02_triggers_pg.sql` + `03_views_pg.sql`. Acceso: `psql -U postgres -d "IstArgentina"` (socket local, sin sudo). Verificada: conteos 56/56, checksums MD5 idénticos, 4 pruebas negativas OK, FKs 98=98, CHECKs 55=55. Backup pre-migración: /tmp/backup_pre_migracion_2026-09-12.sql. La app aún apunta a MySQL — migrar la capa de datos (PDO mysql->pgsql) es el paso pendiente. Skill obligatoria para trabajo PG: `postgresql-architect`.
- **Backend**: `api/` PHP 8.5 + PDO. Router `api/index.php` (recurso → `XHandler::manejar($metodo, $resto)`), handlers por dominio en `api/handlers/`, shared en `api/src/` (Auth, Codigos, Tablas, Validador, Database, Responder). Sesión por token Bearer.
- **Frontend**: SPA vanilla por hash (`#/vista`). Vistas `js/ui/vistas/*.js`, capa de datos `js/datos/api.js` (NegocioRemoto + Store), esquemas de formulario `js/datos/esquema.js`, helpers `js/ui/componentes.js` (UI.tabla/formulario/abrirModal/toast), menú por rol en `js/negocio/autenticacion.js` → `menuPorRol()`, rutas en `js/ui/router.js`.
- **Arrancar**: `php -S 127.0.0.1:8870 api/router.php` → http://127.0.0.1:8870
- **E2E**: `python3 api/tests/e2e.py` — re-seedear ANTES; `KeyError: 'registro'` = BD sucia (por pruebas previas) o PHP caído — NO es bug de código.

## Regla de oro: un apartado por ROL
**Nunca una vista compartida entre roles con diferencias de permisos.** Cuando el usuario pida modelar algo sobre un proyecto de referencia (p.ej. `~/projects/labcontrol`), PRIMERO extrae el menú lateral de CADA rol de ese proyecto (los `<aside>`/nav de sus páginas) y replica una vista + entrada de menú por rol. (Corrección del usuario 2026-09-11: "Soporte Técnico" compartido por jefe y practicante → separado en "Mis Prácticas" del practicante y "Centro de Control" del jefe.)

## Checklist para agregar un módulo
1. **BD** (mysql-architect): tablas + CHECKs + FKs `fk_tabla_col` + filas en `secuencias_codigo` (`INSERT ... ON DUPLICATE KEY UPDATE`) + seed demo que TRUNCATEa y resetea las secuencias.
2. **Handler**: `api/handlers/XHandler.php` + `require` en `api/index.php` + línea de ruta + mapa entidad→tabla en `api/src/Tablas.php`.
3. **Datos JS**: endpoints en `js/datos/api.js` (objeto NegocioRemoto) + formularios en `js/datos/esquema.js`.
4. **Vista**: `js/ui/vistas/x.js` + ruta en `js/ui/router.js` + `<script>` en `index.html` + entrada en `menuPorRol()` con los roles exactos.
5. **Verificar**: E2E ampliado + navegador real por CDP (skill `automation/cdp-chrome-automation`): login de cada rol → tabs renderizadas con datos → acción UI → `SELECT` directo en BD para confirmar persistencia.

## Pitfalls verificados (todos rompieron algo en una sesión real)
1. **Router con prefijo anidado**: en `manejar($metodo, $resto)` una ruta `practicas/emergencias/{cod}/validar` deja el sufijo de acción en `$resto[2]`, NO en `$resto[1]` (ese índice es de rutas de UN segmento tipo `reservas/{cod}/estado`). Síntoma: "Ruta no encontrada" en rutas con acción final.
2. **Hidratación del Store**: cada `ref:` de esquema.js llena su select con `Store.leer(entidad)` ← `GET /api/{entidad}`. La entidad DEBE estar en `$genericas` de `api/index.php` (con su SELECT aplanado por JOIN en `EntidadesHandler::listar`) — si no, el endpoint da 404 y el select queda VACÍO silenciosamente; el formulario falla con "no encontrado".
3. **E2E `req()`**: firma `req(metodo, ruta, token, cuerpo)` donde token es un STRING plano, no un dict de headers.
4. **Modales**: `UI.abrirModal` usa `<dialog id="modal-generico">`; los botones de acción viven en `#modal-acciones` (en tests: `[...dlg.querySelectorAll('#modal-acciones button')].find(b => b.textContent.trim() === 'Guardar')`).
5. **UI.formulario**: soporta `tipo` number/date/time/email/textarea y `opciones:`/`ref:` (select). Un tipo nuevo requiere extender el helper en `js/ui/componentes.js` (así se añadió `textarea`).
6. **CSS de vistas**: las clases que use la vista deben existir en `css/componentes.css` (`.metrica`/`.metricas`, `.dato`/`.dato-et`/`.dato-valor`, `.tarjeta-fila`, `.chip-*` ya están). No inventar archivos CSS nuevos.
7. **Unicidad condicional en BD** (anti-doble-préstamo/reserva): columna generada `vigente_x TINYINT GENERATED ALWAYS AS (IF(estado='X',1,NULL)) STORED` + `UNIQUE(entidad, vigente_x)` — patrón completo en mysql-architect `references/schema-design.md`.
8. **Login por tarjetas de rol**: `login.js` exige que el rol de la cuenta coincida con la tarjeta elegida → un rol sin `.rol-card` en `index.html` NO puede entrar desde la web aunque la API lo acepte. Al crear un rol: tarjeta + botón `.login-cuenta` de autocompletado.
9. **Login por CDP (verificación en navegador)**: sin tarjeta elegida, `VistaLogin.rol` es null y el submit entra y SALTA al login de roles de nuevo (login.js:42-47: rol de la cuenta ≠ null → `Sesion.salir()`). La secuencia VERIFICADA por automatización: (a) `document.querySelector('#vista-roles .rol-card[data-rol="ROL"]').click()` → (b) `[...document.querySelectorAll('.login-cuenta')].find(b => b.dataset.u === 'USUARIO').click()` → (c) `document.getElementById('form-login').requestSubmit()` → (d) navegar con `location.hash = '#/vista'`. Para egresada demo: tarjeta `Estudiante` + cuenta 71893456 (NO existe tarjeta "Egresado").

## Egresado = ESTADO, no rol (2026-09-12)
"egresado" es un ESTADO del alumno (EXISTS en egresos), no un rol: al confirmar egreso el alumno conserva su usuario Estudiante y su portal desbloquea "Mi Egreso" por flag (`usuario.egresado` en login y /me; `soloEgresado` en menuPorRol). `chk_usuarios_rol` NO admite 'Egresado' (migración `2026-09-11_egresado_estado_no_rol.sql`). `avisos.rol_destino` SÍ mantiene 'Egresado' como AUDIENCIA — el fan-out de AvisosHandler entrega por EXISTS(egresos), no por rol. Verificado: E2E 112 checks + navegación CDP real.

## Buzón de avisos (2026-09-11)
`avisos` + `avisos_destinatarios` (fan-out: 1 aviso + 1 fila por destinatario con `leida` individual; FK real a usuarios, cosa que `notificaciones` polimórfica no puede tener). Handler `AvisosHandler` bajo recurso `avisos`: `GET /avisos/buzon`, `GET /avisos/buzon/no-leidas` (campana), `POST /avisos/buzon/{cod}/leer` (solo la propia), `GET /avisos` (stats % leídos), `POST /avisos` (rolDestino o destinatarios[], gate 0-entregas=rollback), `DELETE /avisos/{cod}` (CASCADE retira de todos). Vistas: "Mi Buzón" (TODOS, pestaña 2 = notificaciones del sistema) y "Avisos" (Admin/Sec). Campana con badge: `App.campana()`. E2E: 112 checks.

## Pitfall: seed que inserta filas DEBE avanzar la secuencia
Si un seed inserta filas con código fijo (p.ej. AVI-0004), la `secuencias_codigo` de esa entidad DEBE quedar en max+1 en el mismo seed — si no, la app genera un código duplicado (1062 Duplicate entry) en el primer INSERT real. En 06_seed_egresados.sql la secuencia 'avisos' se resetea a 5 por el AVI-0004 que inserta.

## Expedientes de egresados (2026-09-14, fases BD+app COMPLETAS)
3 tablas: `requisitos_catalogo` (categoría + **rol_autorizado** — la diferencia vs requisitos_tipos_tramite: delega quién evalúa cada requisito), `expedientes` (cabecera estudiante+carrera, un vigente: `uq_exp_vigente` parcial PG / columna generada `vigente_exp` MariaDB), `expedientes_detalle` (UNIQUE expediente+requisito, CHECK coherencia: estado≠Pendiente exige evaluado_por+evaluado_en). **El estado general lo deriva solo el trigger** `trg_expdet_estado`/`expdet_sincroniza`: todos Validado→Completo, alguno Observado→Observado, ninguno evaluado→Pendiente, resto→En revisión. Archivos: `api/sql/12_expedientes.sql` (PG) + `api/sql/mariadb/12_expedientes.sql` (re-ejecutable, DROP PROCEDURE/TRIGGER IF EXISTS) con seed integrado (6 requisitos, 4 expedientes, 24 detalles). Handler `ExpedientesHandler` (`/expedientes`): GET listar (Estudiante solo los suyos por `Auth::estudianteDeUsuario`), GET detalle aplanado, POST abrir (fan-out detalles desde catálogo activo, rechaza duplicado vigente con código en el mensaje), POST `/{cod}/requisitos/{rq}/evaluar` + `/pendiente` (gate por rol_autorizado; Observado exige observación), DELETE (CASCADE). Vista `expedientes.js` por rol: Sec/Admin (listado+catálogo CRUD+detalle `#/expedientes/{cod}`), Tesorería (bandeja SOLO requisitos Pagos), Estudiante (tarjetas de avance por expediente, sin acciones). Menú id `expedientes` para los 4 roles. E2E 137 checks. Pitfalls verificados: (1) ruta anidada `{cod}/requisitos/{rq}/{accion}` → sufijo en `$resto[3]`; (2) `renderizar()` valida vista contra menú → la ruta de detalle (`expediente-detalle`) necesita caso especial en Router.renderizar; (3) `evaluar` devuelve el expediente completo con estado YA derivado (el handler nunca escribe estado_general); (4) al usar `Codigos::siguiente` dentro de una transacción del handler se une a ella (FOR UPDATE).
